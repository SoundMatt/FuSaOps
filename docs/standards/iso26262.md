# ISO 26262 — Road vehicles, functional safety

FuSaOps supports ISO 26262 by orchestrating per-language tools and aggregating
their evidence across a mixed-language item. FuSaOps itself is developed as an
**ASIL-C** tool (see `.fusa.json`, `.fusa-hara.json`, `docs/qualification.md`).

## How FuSaOps contributes

| ISO 26262 area | FuSaOps contribution |
|---|---|
| Part 6 §8–9 (unit design / verification) | Aggregates each language tool's lint/static-analysis findings into one gate |
| Part 6 §6 (software safety requirements) | Requirements registry (`.fusa-reqs.json`) + `gofusa trace` across the toolchain |
| Part 3 (HARA) | `.fusa-hara.json` for the tool itself; per-component HARAs roll up via each tool |
| Part 8 §11 (tool qualification) | `gofusa qualify` per tool; FuSaOps qualification in `docs/qualification.md` (TCL2) |
| Part 8 §7 (configuration mgmt) | Tagged releases, committed evidence, SBOM/provenance |

## Per-language depth

ISO 26262 clause-level gap assessment for each language is produced by that
language's tool (e.g. `gofusa iso26262`, `cpfusa iso26262`). FuSaOps runs them
and presents the aggregate; it does not re-derive clause mappings.

## ASIL handling

Each tool determines ASIL from its own HARA/config. FuSaOps preserves severity
and attribution so the aggregate gate reflects the highest-criticality findings
across languages.
